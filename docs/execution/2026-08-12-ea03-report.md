**状态:** complete

## 1. 问题摘要

外审 EA-03 两条独立缺口：

- **序列 A：** write proposal DTO 把 raw `approval_grant` 交给渲染层；批准时再回送。process DTO 的 `decision_available` 是正确对照。
- **序列 B：** 空 pattern 只在 TS gateway 拦截；原生 command 与 SQLite `validate_pattern` 均不拒空；kernel 把空 pattern 当作 match-all。

目标：renderer 只拿非授权可用性布尔位；决定命令由 host 查 grant；空/trim/长度等不变量在原生与 repository 双层校验。

## 3. 实现记录

### 序列 A — write grant host-private

1. `WriteProposalDto`：`approval_grant: Option<String>` → `decision_available: bool`（与 process 同构注释）。
2. `list_write_proposals`：`decision_available = view.approval_grant.is_some()`，**从不**拷贝 grant 到 DTO。
3. `decide_write_proposal(conversation_id, proposal_id, decision)`：服务层在 owner-scoped host 上 list 出 live grant，再调用 `runtime_host.decide_write_proposal`；**不接收**渲染层 grant。
4. Tauri `decide_write_proposal` 命令签名去掉 `approval_grant`。
5. Renderer：`WriteApprovalBar` / `Workbench` 使用 `decisionAvailable`；删除 `grantByProposalRef`；decide invoke 只带 conversation/proposal/decision。
6. 网关闭合 key：`approvalGrant` 删除，`decisionAvailable` 必填 boolean；wire 上再出现 `approvalGrant` 一律 `invalid_write_response`。

### 序列 B — 空 pattern 原生拒

1. `validate_pattern`：拒 `is_empty()` 与 `trim().is_empty()`（仍拒超长与 NUL/CR/LF）。
2. `SqlitePermissionRuleRepository::add`：先 `trim` 再 validate，**存 trim 后** pattern。
3. `add_permission_rule_impl`：command 层再 trim + 拒空（`permission_rules_invalid_pattern`），不依赖 TS。

### 先红后绿（方法）

- 序列 A：在旧契约下，序列化 DTO 会带 `approvalGrant`；新测试断言仅有 `decisionAvailable` 且无 grant key → 旧码红 / 新码绿。
- 序列 B：旧 `validate_pattern`/`add_permission_rule_impl` 接受 `""`；新测试 `expect_err(InvalidPattern)` / `permission_rules_invalid_pattern` → 旧码红 / 新码绿。
- 实现时先写负向测试再改产品代码；收口时整包 crate 测试均为绿（见退出码表）。

## 7. 残留风险

1. **decide 两步查 grant：** service 先 `list_write_proposals` 再 `decide_write_proposal`（runtime-host API 仍要 grant 字符串）。并发双点批准时第二方应 fail-closed（grant 已消费 / not live）。理想形态是 host 内原子「按 id 决定」API；未改 `crates/runtime-host`（本单禁止/非必要）。
2. **无完整 live write E2E：** 序列 A 的 grant 查找路径用 DTO 序列化 + 源码契约 + 网关白名单钉住；未在本 worker 起真实 pending write 做端到端批准（总控 E2E 范围）。
3. **历史 DB 若已有空 pattern 行：** 读路径 `validate_pattern` 会把该行当 `InvalidStoredRule` 拒；本单未写迁移清理（产品上应极少，因 UI 一直拒空）。
4. **「一次用户动作上下文」：** 与 process 一致依赖 window/project scope + conversation ownership + live host grant；没有额外 UI gesture token（process 也没有）。
5. **同源脚本仍可 invoke decide：** 去掉 raw grant 后，脚本不能偷 grant，但仍可对 `decision_available` 的 pending 发 `approve_once`。这与 process 现状相同——信任边界是 host 持有 grant + 窗口/项目 scope，不是「renderer 无法发 IPC」。
6. **`write_invalid_grant` 错误码** 仍保留（host 内部 digest 校验），renderer 不再有机会送错 grant，该码出现面收窄。
