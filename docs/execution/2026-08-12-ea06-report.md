## 2. Decision: escape (human audit) + reject (protocol Format controls)

**Primary product choice: escape on the human-audit display path.**

| Layer | Behavior | Why |
| --- | --- | --- |
| Machine-readable argv / receipt | Unchanged raw `string[]` | Acceptance #4: display must not mutate sealed structure |
| Human-audit display (`formatArgvDisplay` / shell display) | Explicit `\uXXXX` for bidi **formatting** controls | Approval decision must not depend on browser bidi reordering |
| `agent-protocol` validate | **Reject** listed bidi formatting controls in process argv and path components | Closes the cited `char::is_control` gap (Format ≠ Control) |
| UI | Per-token `<code class="…argv-token">` + CSS isolate | Second layer only; not sole defense |

### Why not “reject only”?

Reject-only at protocol would leave host/renderer DTOs (and any path that skips this crate — e.g. `tool-executor` is out of allowlist and still only checks `is_control`) able to paint raw Format chars. Acceptance also requires a safe human-audit representation without rewriting receipt argv.

### Why not “escape only”?

Audit cites `validate.rs` only checking `char::is_control`. Leaving Format controls accepted at the protocol boundary keeps a known social-engineering vector in sealed proposals. Rejecting **formatting controls** (not RTL letters) does not block Arabic/Hebrew filenames.

### Why reject does **not** break legitimate RTL filenames

Arabic/Hebrew **letters** are script characters, not bidi *formatting* controls.  
Examples that still validate: `ملف.txt`, `שלום.js`, `docs/ملف/readme.md`.  
Attack examples rejected: `photo` + U+202E + `gnp.exe`.

### Escape cannot re-decode when painted as text

`escapeBidiFormattingForDisplay` replaces Format code points with ASCII sequences (`\` `u` hex). Rendered via React text content (not `innerHTML` / `dangerouslySetInnerHTML`), those six characters never become U+202E again.

## 6. Residual risk

1. **`tool-executor` / host process validation** still use `char::is_control` only (out of allowlist). A proposal that never passes `agent-protocol` validate could still reach OS with Format chars; UI escape + isolation covers the human decision surface for DTOs that do reach the renderer.
2. **Unlisted Format / direction marks** (U+202C, U+200E/F, U+061C, zero-width, etc.) are not rejected or escaped. Strong RLO/isolate spoofs from the audit list are covered; weaker marks remain residual.
3. **CSS isolation is second layer only.** If escape were removed, isolate still limits *cross-token* influence but would not neutralize Format chars *inside* a single token. Escape remains the approval safety boundary.
4. **No WebView2 screenshot** was captured (audit also left this unobserved). Unit tests assert DOM text and structure, not pixel order under real bidi layout engines.
5. **Shell “character-identical” contract** now has an intentional exception: bidi formatting controls are escaped in shell display too. Commands without those controls remain character-identical.

## 7. Implementation notes

### Protocol

```text
is_bidi_formatting_char ∈ { U+202A, U+202B, U+202D, U+202E, U+2066..=U+2069 }
validate_process_argv: reject if any char is_control || is_bidi_formatting_char
validate_project_path_inner: same for path components
```

### Display (dual representation)

```text
machine argv: proposal.argv / activity.argv  — raw, never rewritten
human audit:  escapeBidiFormattingForDisplay(JSON.stringify(arg))  per token
shell:        escapeBidiFormattingForDisplay(argv[0])  — no JSON wrap
```

### UI

- Host element keeps `data-testid="command-approval-argv"` / `command-activity-argv` for expand + `data-full-command` / `title`.
- Each sealed token is a child `<code data-testid="command-argv-token" class="…argv-token">`.
- CSS: `unicode-bidi: isolate; direction: ltr` on tokens.
