## 2. EA-01 — Windows 路径大小写别名绕过项目 deny

### 2.1 复现（先红后绿）

**原问题序列（审计）**  
deny `edit:blocked/**` + mode `accept_edits`/`bypass` + proposal path `BLOCKED/SECRET.TXT` → 字面匹配 miss → mode 自动批准 → OS 解析到同一文件。

**复现测试**

| 测试 | 位置 | 断言 |
| --- | --- | --- |
| `windows_write_edit_deny_folds_path_identity_allow_stays_strict` | `crates/kernel-policy/tests/permission_rules.rs` | Windows：deny `blocked/**` 命中 `BLOCKED/SECRET.TXT`；allow 同 pattern 不命中（大小写严格） |
| `windows_case_alias_modify_cannot_bypass_project_deny_under_auto_modes` | `crates/runtime-host/tests/governed_write_bridge.rs` | 实文件 `blocked/secret.txt`；bypass/accept_edits；modify `BLOCKED/SECRET.TXT` → Rejected、内容不变、无 mode receipt、有 deny rule receipt |
| `windows_case_alias_create_under_denied_parent_is_blocked` | 同上 | create `BLOCKED/new.txt` under write deny → 无写入、无 mode receipt |

旧契约测试 `SRC/**` 不匹配 `src/lib.rs`（标注 “case-sensitive on every platform”）已改写：

- **raw** `permission_rule_matches` 仍对路径大小写敏感（allow 与显式 matcher API）。
- **deny** 的 path identity fold 只在 `evaluate_permission_rules` 内、且仅 write/edit + Deny。
- **为何旧契约错**：它把「规则字面匹配」当成「OS 对象身份」。在 Windows 默认大小写不敏感卷上，二者不是同一个东西；用字面敏感 deny 会在 mode 自动批准前漏掉别名。

### 2.2 修复

**`crates/kernel-policy/src/permission_rules.rs`**

- 新增 `path_deny_uses_identity_case_fold()`（`cfg!(windows)`）。
- `evaluate_permission_rules`：write/edit **Deny** 走 `path_deny_matches`（Unicode `to_lowercase` 后 portable-path 通配）；write/edit **Allow** 与 process 仍走原 matcher。
- `match_subject` 仍记录提案原始 path（满足 storage `match_subject == path`，不扩大 DTO）。
- 模块文档写明每平台语义。

**adapter-grok-acp**：未改。provider 仍保留组件大小写；治理在 host 规则评估前以 identity fold 对齐 deny。无需渲染层改 path 即可关闭 EA-01。

### 2.3 每平台语义

| 平台 | write/edit **Deny** | write/edit **Allow** | 说明 |
| --- | --- | --- | --- |
| **Windows** | 大小写折叠后匹配（fail-closed：宁可多 deny） | 大小写敏感 | 对齐 NTFS 默认 case-insensitive 对象身份；allow 收窄避免别名误自动批准 |
| **non-Windows** | 大小写敏感 | 大小写敏感 | 对齐典型 Unix 大小写敏感卷 |
| **macOS 等可能 CI 卷** | 同 non-Windows（本修复未折叠） | 同左 | **残留**：默认 APFS 常为 case-insensitive，deny 字面敏感仍可能漏别名。若产品要覆盖，应另开 `cfg`/`runtime probe` 设计，不在本单静默改 Unix 行为。 |

**Allow vs Deny 故意不对称**：accept_edits/bypass 在 RequireConfirmation 时仍可自动批写；只有 **deny 命中** 能硬停。因此 deny 必须按 OS 身份更宽，allow 保持更严。

## 3. EA-02 — process rule subject 丢失 argv 边界

### 3.1 复现（先红后绿）

| 测试 | 断言 |
| --- | --- |
| `process_subject_collision_matrix_keeps_argv_boundaries` | `["safe.js","--version"]` 与 `["safe.js --version"]` subject **不等**；allow `node safe.js *` 只批前者 |
| `legacy_flat_process_subjects_fail_closed_for_allow` | 旧扁平 `"node safe.js --version"` 不 decode、不匹配、不 confirm |
| `process_allow_rule_does_not_cross_argv_boundaries` | Host：default mode + allow `node safe.js *` + argv 单元素含空格 → 需人类、rule 不自动批 |
| `canonical_process_subject_is_injective_and_reversible` | 空 argv / 含空格 argv round-trip；禁止退回纯空格拼接 |
| `rule_subject_argv_is_identical_to_execution_argv` | decode 出的 argv 与 executor 将使用的 `OsString` argv 同一 |

### 3.2 可逆编码方案（v1）

`canonical_process_subject(program, argv)`：

- 空 argv → `{program}`（兼容 storage：`match_subject == program \|\| starts_with(program + " ")`）
- 非空 → `{program} \u{1e}p1` + 每个 arg `:{hex_utf8_byte_len}:{utf8}`

`decode_process_subject` 严格反解；失败 → 当作遗留/损坏。

**Pattern 匹配**

- 能 decode 且 argv **双射**于空格拼接（无空 token、token 内无空格/RS）→ 用历史 Grok 风格字符前缀/通配表面（`cargo *`、`node*` 等仍有效）。
- 非双射（含空格/空参等）→ 只对 **规范编码串** 做 starts_with/wildcard，避免 `node safe.js *` 撞上 `["safe.js --version"]`。
- 无法 decode 的 subject + 非空 pattern → **不匹配**（fail-closed）。

Shell 分段 `conservative_shell_command_segments` 改为输出同一 v1 subject，不再 `tokens.join(" ")`。

### 3.3 规则/执行 argv 同一性

- Host 规则：`canonical_process_subject(sealed.program(), sealed.argv())`
- Executor：`sealed.execution_argv()` ← 同一 `sealed.argv` 转 `OsString`
- 测试钉住：decode(subject)[1..] == execution argv（含空格/空参矩阵）

## 4. 旧规则迁移策略与依据

| 对象 | 策略 | 依据 |
| --- | --- | --- |
| 已存 **pattern** 为简单 toolchain 形（`cargo *`、`node --version`） | 继续对 v1 subject 的双射表面匹配 | 用户意图未变，argv 无空格时行为兼容 |
| 已存 **pattern** 等于旧扁平 subject 且 argv 曾含空格 | **不再自动匹配** → RequireConfirmation | 旧 subject 非单射，静默继续匹配会保留 confused deputy |
| 运行时传入的 **旧扁平 match subject** | decode 失败 → allow 不确认、非空 pattern 不命中 | fail-closed 优于静默放行 |
| 新收据 `match_subject` | 一律 v1 | 与执行 argv 同构 |

**不选**「继续用空格拼接并尽量猜边界」：审计已证明边界不可恢复。

### 6.2 残留风险

1. **macOS/CI 大小写不敏感卷**：non-Windows deny 仍字面敏感（见 §2.3）。  
2. **Windows 非 ASCII 大小写 / 短名 8.3**：使用 Unicode `to_lowercase`，非完整 Win32 case mapping；极端别名可能仍漏。fail-closed 方向是「多 deny」，短名另案。  
3. **process allow 过宽 pattern**（`node*`）：仍可批准任意 node argv（含空格文件名）；这是 pattern 宽度问题，非边界碰撞。  
4. **渲染层仍按空格拆 subject**：用户可能存出错误 pattern，直到 §5 接线。  
5. **FS 级 canonicalize 未做**：本修复在纯 policy 层做 identity fold，不依赖 project root 遍历；与 executor 逐组件 OS 解析在 Windows 默认语义下对齐 case 别名。symlink/reparse 仍由既有 write executor 边界负责。
