# 并发语义:一个活对话 + 受治理的派单

日期:2026-08-13 · 维护者拍板 · 取代此前一切"槽位同时工作"的说法

## 结论

**Pillow 不承诺多个槽位同时运行。**

- 槽位是**长期保留的配置**,可以有很多个
- **同一时刻只有一个槽位在跑活对话**
- 其他角色通过**总控派单**干活,派单走既有的受治理 process 链
- 用户要能在时间线上**看见**派单发生了、谁在做、结果回来了

## 为什么要写这份

在此之前,产品叙事和实现是矛盾的:

- 文案、简报、汇报里一律说「槽位可共存、**同时工作**」
- 代码里 `apps/desktop/src-tauri/src/runtime_composition.rs:51` 是
  `HostConfig::new(1, false, 64)` —— `max_concurrent_turns = 1`
- `runtime_service_state.rs` 切槽位时 `previous.shutdown()`,**关掉上一个**

也就是说「共存」只在**记录层**成立,运行时层从来不成立。

🔴 **这不是实现落后于设计,是我(总控)反复把一个不存在的性质当成事实陈述**,
还把它写进派单简报当作不可破条款,让 Worker 去保护一个并不存在的东西。
是 2026-08-13 的多 agent 调研读代码时发现的,不是自查发现的。

两套说法同时成立会把后续 UI 和适配器做歪 —— 这是选 B 的直接理由。

## 被否决的方案

**A. 宿主按 `slot_id` 持有 N 个运行时。** 能力最强,但代价不在"起多个进程",
而在**审批仲裁**:多个运行时同时提交审批,谁先谁后、归属哪条时间线、
一次批准覆盖谁 —— 这是一整轮设计,而且会动到目前唯一经过外审的那条链。

没有否定 A 的价值,只是它不是现在该付的代价。

## 这份决定管住什么

1. 🔴 **任何文案不得再说「同时工作」/「并行运行」。**
   准确说法:**可配置多个、长期保留;一个在对话;其余靠派单。**
2. 派单必须在时间线上可见 —— 用户看不见的能力等于没有。
3. 将来若要做 A,**先解决审批仲裁**,再谈多运行时。
